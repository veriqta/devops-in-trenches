# Contributing to DevOps in the Trenches

Thank you for helping improve DevOps in the Trenches.

This repository supports a proprietary book project. It accepts focused corrections and reader feedback, but it is not an open-authoring project. Ann Ogechi Felix retains authorship, copyright ownership, editorial direction, and final decision authority.

Read this guide before opening an issue or pull request.

## Contributions We Welcome

The most useful contributions are precise, evidence-based, and limited in scope.

We welcome:

- Corrections of technical facts.
- Corrections of spelling, grammar, punctuation, and formatting.
- Reports of broken, redirected, or outdated links.
- Corrections to commands, examples, tables, and terminology.
- Reports of contradictions between repository files.
- Accessibility improvements.
- Suggestions for authoritative primary sources.
- Clarification requests where wording could lead to unsafe or incorrect application.
- Reports that a checklist item lacks context, ownership, evidence, or verification criteria.
- Reader feedback on public samples.

## Contributions We Do Not Accept Without Prior Invitation

Do not submit the following unless the repository owner has requested them:

- Complete chapters or large chapter rewrites.
- A replacement table of contents.
- Unsolicited translations.
- New book editions, forks, or derivative curricula.
- Vendor marketing content or sponsored placement.
- Promotional links with no direct editorial value.
- Generic blog posts or tutorials.
- Generated bulk content.
- Confidential company material.
- Real credentials, tokens, private keys, customer data, or internal incident evidence.
- Exploit instructions that create unnecessary risk.
- Material copied from another publication, course, repository, or website.

Large unsolicited pull requests may be closed without detailed review.

## Before Reporting an Issue

1. Confirm that the issue affects the current repository version.
2. Search open and closed issues for an existing report.
3. Identify the exact file, heading, table, paragraph, or link.
4. Separate factual errors from design preferences.
5. Gather an authoritative source when the correction depends on external facts.
6. Remove confidential or identifying information.

Use official standards, specifications, primary research, and project documentation where possible. Search-result snippets, anonymous posts, and unsupported vendor claims are normally insufficient evidence for a technical correction.

## Choose the Correct Issue Type

### Technical correction

Use this for an inaccurate technical statement, unsafe instruction, incorrect command, invalid configuration, misleading definition, or material omission that changes the meaning of the guidance.

Include:

- File and section.
- Current wording or behavior.
- Why it is inaccurate or unsafe.
- Proposed correction.
- Supporting authoritative sources.
- Affected version, platform, or environment.

### Broken link

Use this for an unavailable, redirected, misleading, or replaced reference.

Include:

- File and section.
- Broken URL.
- Date checked.
- Recommended official replacement, if available.

### Reader feedback

Use this for clarity, structure, accessibility, navigation, or practical-use feedback that is not a factual correction.

Explain what you expected, what was unclear, and how the problem affected your use of the material.

## Pull Request Rules

Open a pull request only when:

- An issue template directs you to do so.
- A maintainer requests a patch.
- The change is small, obvious, and limited to spelling, formatting, or a verified broken link.

Each pull request should:

- Address one issue or tightly related group of corrections.
- Use a clear title.
- Explain why the change is needed.
- Link the relevant issue.
- Preserve the existing voice and structure.
- Avoid unrelated reformatting.
- Update internal links when files move.
- Include authoritative evidence for technical changes.
- Pass available repository checks.

Do not combine editorial rewrites, policy changes, curriculum changes, and technical corrections in one pull request.

## Writing Standard

Accepted text should use:

- Clear and direct language.
- Active voice where practical.
- Short or medium sentences.
- Specific nouns and verbs.
- Standard technical terminology.
- Consistent headings and list structures.
- Enough context to apply guidance responsibly.

Avoid:

- Marketing claims.
- Unexplained jargon.
- Artificial urgency.
- Tool worship.
- Universal claims without evidence.
- Blame-focused incident language.
- Invented measurements or test results.
- Generic filler.
- Content that sounds like a search-optimized blog post.

The book uses production scenarios to teach reasoning. Proposed examples should make ownership, evidence, decisions, consequences, and recovery visible.

## Technical Evidence Standard

Technical corrections should prefer sources in this order:

1. Official standards and specifications.
2. Primary research.
3. Official project and product documentation.
4. Established books and professionally reviewed publications.
5. Credible secondary analysis when primary material is unavailable.

State when a recommendation is context-dependent. Include relevant versions, dates, environments, or constraints.

Do not claim that a configuration was tested unless you performed and documented the test. Do not invent command output, benchmark results, incident evidence, or implementation success.

## Safety and Confidentiality

Never submit:

- Passwords, API keys, tokens, certificates, or private keys.
- Customer, employee, or personal information.
- Internal hostnames, account identifiers, or private addresses.
- Confidential architecture or incident records.
- Unreleased vulnerability details requiring coordinated disclosure.
- Proprietary documents or licensed training material.
- Information obtained without authorization.

Use fictional and clearly marked examples. Redact sensitive details before attaching logs or screenshots.

If a report may create security risk, do not post it publicly. Use a private security-reporting method when one becomes available.

## AI-Assisted Contributions

Contributors remain responsible for every submitted statement, regardless of the tools used to draft it.

Do not submit unreviewed generated content. Verify factual claims, citations, commands, links, and terminology. Disclose material AI assistance when a pull request contains substantive drafted text.

Generated text does not excuse plagiarism, inaccurate attribution, fabricated sources, or exposure of confidential information.

## Review and Editorial Decisions

Submission does not guarantee acceptance.

A contribution may be edited, deferred, declined, or closed because it:

- Falls outside the book's scope.
- Duplicates an existing report.
- Lacks evidence.
- Conflicts with the editorial direction.
- Creates repetition.
- Requires broader restructuring.
- Introduces legal, privacy, security, or licensing concerns.
- Is better addressed in a later edition.

The repository owner has final authority over wording, structure, timing, attribution, and publication.
